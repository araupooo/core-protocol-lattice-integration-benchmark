Core-Protocol Lattice Integration Benchmark and Remediation

OpenSSL 3.0.13 + oqs-provider 0.12.0 + liboqs 0.16.0 · TLS 1.3 · Hybrid key exchange X25519MLKEM768 (group 0x11ec) · ML-DSA-65 · Machine: AMD EPYC 9D25, AVX2/AVX512, Ubuntu 24.04

What was measured

Two liboqs builds from the same pinned tarball — reference (OQS_OPT_TARGET=generic, no AVX2) and optimized (OQS_OPT_TARGET=auto, native AVX2) — each with its own oqs-provider 0.12.0 build, driven through the real TLS 1.3 call path (openssl s_server / s_client, loopback). Parameter sizes asserted at runtime against FIPS 203 Table 3 and FIPS 204 Tables 1–2.

Honest scope: the optimized build shows no measurable handshake wall-clock improvement (18 ms vs 19–21 ms medians, within run-to-run noise). Wall time is dominated by s_client process spawn and scheduling (~15 ms floor even for resumed handshakes); the crypto gap (~0.3 ms per handshake) is two orders of magnitude below that floor. The 4–7x benefit is proven at the crypto-operation layer only; a throughput benefit for in-process / high-throughput servers is plausible but unmeasured and is not claimed here.

Finding B-1 — ML-DSA-65 server certificates cannot be served by OpenSSL 3.0.13

openssl s_server exits immediately with an ML-DSA-65 (or hybrid p384_mldsa65) server certificate:

error setting certificate
SSL_CTX_use_certificate: ca md too weak            (default security level)
ssl_set_cert: unknown certificate type             (SECLEVEL=0)

Mechanism (OpenSSL 3.0.13 ssl/ssl_rsa.c): SSL_CTX_use_certificate() first calls ssl_security_cert(), which rejects digest-less ML-DSA signatures; then ssl_set_cert() calls ssl_cert_lookup_by_pkey(), whose table only knows built-in key types — provider-defined keys are not in it.

Reproduced deterministically by scripts/reproduce_bottleneck.sh (3/3 cases): outputs/before-remediation-case1-mldsa65-default.log, outputs/before-remediation-case2-mldsa65-seclevel0.log, outputs/before-remediation-case3-hybrid-p384mldsa65-seclevel0.log.

Remediation

R-1 — Authenticate with a classical ECDSA P-384 certificate while keeping the hybrid X25519MLKEM768 key exchange. Patch: src/remediation/server-config.patch (applies cleanly with patch -p1; after-state: src/remediation/server-config.cnf). After the patch all handshakes succeed (see TLS table above). ML-DSA-65 is still exercised at the liboqs API level and the X.509 level (openssl verify chain OK).

R-2 — Ship the optimized liboqs build (OQS_OPT_TARGET=auto): 4–7x faster at the crypto layer (table above).

R-3 — Keep TLS 1.3 session resumption enabled (default): resumed medians 14–15 ms vs full 18–21 ms (~17–29% faster).

Regression tests (scripts/run_tests.sh): 6/6 pass — B-1 pinned behaviour, post-remediation handshakes, liboqs round-trips + FIPS sizes, optimized KEM round < 50% of reference, patch round-trip, ML-DSA-65 chain verification. Log: outputs/test-output.log.

Limitations — disclosed

  • ML-DSA-65 certificates in a live TLS server are unproven on this stack. Whether a newer OpenSSL branch accepts them was not tested; no claim is made about OpenSSL 3.2/3.4/3.5.
  • No in-process / high-throughput TLS measurement. The optimized build's speedup is proven at the liboqs layer only.
  • Single machine, loopback, small samples. TLS numbers are 30+30 handshakes per build (two runs); liboqs numbers are 200/100 iterations. No network latency, no concurrency, no multi-client load.
  • Certificates are test-only (CN=localhost, 1–2 day validity, regenerated fresh per run).
  • liboqs / oqs-provider carry no FIPS 140-3 validation and are not recommended for production use by their projects. This is a benchmark and integration assessment, not a deployment recommendation.
